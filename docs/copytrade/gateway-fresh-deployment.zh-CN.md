# Discord 事件采集：全新安装与验收

适用于全新数据库、交易所空仓且无普通/条件挂单的部署。本次不迁移旧数据库、不接管旧交易、不补执行历史信号。不要将本文命令用于覆盖仍有交易状态的旧 data 目录。

## 运行结构与职责

```
Discord Gateway → Python 持久缓冲 → 私有 Unix Socket → Go 入库事务
  → 不可变消息修订 + 每交易员顺序投递 → 解释 → 统一风控/订单/保护/恢复
```

- `collector/`：Python 3.12、`discord.py-self==2.1.0`；全部 Python 依赖锁定并校验哈希。没有桌面、浏览器、公网监听端口，也不接触交易所密钥。
- `discord/source.go`：单一采集入口、配置确认、不可变规则快照、按交易员串行投递、执行边界。
- `copytrader/notifications.go`：Chroma 的有限确定性解释、共同后置检查、历史目标关联。复杂文案继续走原 AI。
- 新增、部分字段编辑、删除和批量删除均记录。删除不直接撤单或平仓。
- 新消息先写采集器 SQLite WAL；Go 事务提交后才 ACK。ACK 丢失重传相同事件，语义修订和动作账本再次去重。
- 采集缓冲上限 128 MiB，Go 未完成投递上限 10,000。压力或存储异常通过状态/告警暴露；保留待交付事件，阻止不可靠情况下新增风险。
- 配置版本随采集时的事件保存。消息在缓冲里等待时切换规则，不会改用新规则解释旧事件。仅文字说明变更可继续使用已冻结解释；停用和执行条件变更使未提交的旧开仓失效。
- 采集器采用文件锁；部署仅运行一个采集实例，共用一个持久缓冲目录。SDK 管理 Gateway 重连，容器只监督进程退出。

这里的“无轮询”指取消周期性频道历史拉取和 `/quests/@me` 探测。Gateway 心跳、Go 本地队列检查、网页状态查询及原有交易所保护核对仍是必要的独立机制。

## 安装

Ubuntu 24.04 amd64 的一键安装、原更新命令和前端邮件配置见 [安装与邮件说明](install-and-email.zh-CN.md)。

```bash
curl -fsSL https://raw.githubusercontent.com/linlea666/joz/main/install.sh -o /tmp/nofx-install.sh
sudo bash /tmp/nofx-install.sh
# 日常更新
cd /opt/nofx && ./start.sh update
```

首次部署前确认账户空仓且无普通/条件挂单。安装自动生成配置和密钥，新数据库默认仅采集验证。邮件在页面单独保存，无须手写 SMTP 环境变量。

本方案使用 `docker-compose.yml`，其中新增 `discord-collector`。不要混用旧的 `docker-compose.prod.yml` 镜像部署入口；旧发布镜像不包含此次代码。

持久化资源：

| 位置 | 内容 | 处理原则 |
|---|---|---|
| `./data` | 主数据库、消息、规则快照、交易账本 | 启用后不得当缓存清空 |
| `discord-buffer` Compose volume | 尚未确认的事件、恢复边界、消息合并缓存 | 重启保留，不手动删库消除缺口 |
| `discord-runtime` Compose volume | 权限受限的 Unix Socket | 两容器共享，不对外映射端口 |

## 三位交易员配置

作者风格和来源模式是两个独立设置。更换风格预设不自动改实际来源频道、风险、账户或执行策略。

| 交易员 | 作者风格 | 来源模式 | 来源配置 |
|---|---|---|---|
| CMM | `cmm_v1` | `channel` | 现有实际频道；双价格语义按已确认规则选择“市价＋限价” |
| TYLER | `tyler_v1` | `channel` | 现有实际频道；保留验证过的管理口令和条件 |
| jonzi | `jonzi_v1` | `chroma` | 配置新增通知和更新通知的实际频道，明确当前消息作者过滤 |

已核查的 jonzi 示例（权限与当前实际消息作者请用“频道预览”再核对）：

```json
{
  "primary_channel_id": "1452344484103848026",
  "source_mode": "chroma",
  "source_channel_ids": ["1452556042096611390", "1452556390806585364"],
  "source_author_names": ["JONZi"],
  "interpretation_profile": "jonzi_v1"
}
```

这些字段合并到现有跟单配置，不是完整替换所有风险参数。名称按去除首尾空白、忽略大小写的**精确匹配**；更推荐填核对后的作者 ID。两种过滤同时填写时同时生效。只读卡片上的作者名称不等于当前消息作者，不会绕过过滤。

实际来源非空时覆盖逻辑频道的采集来源，不额外监听原卡作为开仓入口。普通频道原卡结束编辑继续要求唯一原消息关联。

## 先观察，再启用

默认全局执行模式为 `observe`（仅采集验证）。在该模式启动配置好的跟单交易员以建立订阅并检查解释结果，不会根据新信号下单。

1. Discord 设置中保存凭证，检查保存结果与应用结果；“已保存但未生效”需处理具体错误。
2. 启动三个跟单交易员，确认 Gateway 有真实心跳、配置版本一致，各实际频道为 `ready`。
3. 首次频道基线只存为背景。用真实的新消息观察作者过滤、两个通知频道归属、消息编辑、确定性/AI 路径、解释参数与耗时。
4. 日志应串联来源事件 ID、投递 ID、消息 ID/修订、规则快照、解释、交易、动作、订单。验证 AI 的识别结果不等于完成下单。
5. 确认无缺口、无异常积压且账户仍符合空仓无挂单前提，再由操作者将全局模式改为 `live`（正常执行）并保存。
6. 系统记录启用边界。只有之后的新信号可新增风险，验证积压和历史 QNT 不补下单。已有交易保护/订单恢复与 Discord 采集独立。

## Chroma 行为

- `was added`：当前正文授权开仓，附卡/引用只补参数。只有固定、完整且无冲突的简单限价卡走确定性快路径，其他格式走 AI 后仍通过相同来源检查。
- `was updated`：仅允许明确的止损/止盈变更；不能从附带原卡重新开仓。
- `was closed` / 结束通知：保留结束语义，查找唯一历史交易。先前开仓失败或已结束时记录无须操作；待成交时撤销对应入场；有余仓走已有关闭流程。
- 查询失败、提交结果不明或多候选不能当作空仓。不会为了找到仓位而跳过较新失败记录、选取较早同币种交易。
- 明确原卡引用优先于旧卡价格比较，移止损/止盈的新值不会使原交易关联失效；明确指向另一张卡的结束通知不会取消当前待提交开仓。
- 开仓正在等 AI 时，如果结束通知已进入持久收件箱，提交前会阻止该开仓。
- 单条样本的快速采集或成功运行不能说明免受账号限制；个人账号自动化仍受 Discord 平台规则约束。

## 断线与故障恢复

| 状态 | 含义与处理 |
|---|---|
| `connecting` / `reconnecting` | SDK 建立/恢复连接；不启用另一套后台轮询 |
| `recovering` | 新会话核验缺口，完成前不放行新增风险 |
| `ready` | 频道已通过权限与基线/补读核验 |
| `gap` | 10 页×100 条未覆盖缺口，或补读失败；保留最早未验证边界，阻止该来源新增风险 |
| `forbidden` | 频道不存在或无权限；核对实际来源与账号权限 |
| `auth_invalid` | 认证失败，需要操作员处理凭证；不自动轮换账号 |
| `buffer_failed` / `storage_failed` | 缓冲满额/磁盘/数据库异常；先恢复存储，不删除账本重试交易 |
| `stale` / `disconnected` | 缺乏有效心跳或本地连接断开；“已配置凭证”不代表正在正常采集 |

Gateway Resume 成功不拉历史；新会话从已保存进度做有界补读并核验当前活跃交易的原卡。无法覆盖的历史缺口不会随着新消息到达自动清除。长期缺口需人工核对来源和交易，在确认不再需要这些信号后再制定新的启用边界；本期不提供自动丢弃缺口的按钮。

```sh
docker compose -f docker-compose.yml logs --tail=100 discord-collector
docker compose -f docker-compose.yml logs --tail=100 nofx
```

重启可恢复事件和订单身份，不代表“重新下单”。提交结果不明走已有订单查询和恢复。网站未认证请求、Discord 异常和交易所订单异常分别排查。

## 本次本地验证结果

- 七个相关 Go 包通过竞态测试，前端 16 个测试文件、199 项测试通过，前后端构建通过。
- 采集器使用 Python 3.12 虚拟环境，依赖按锁文件与哈希安装；14 项模拟测试通过，涵盖 ACK 丢失、重启、缓冲满额、缺口锚点、首次多页基线、Resume 不拉历史、活跃卡片核验及配置进度恢复。
- 全量 `go test ./...` 已执行：原有 CoinAnk、Hyperliquid 行情集成测试中 13 项因外部接口超时或 DNS 失败未通过；排除这 13 个联网用例后，其余全仓 Go 测试通过。没有为通过测试修改这些行情模块或测试。
- 本地没有 Docker 可执行程序，因此未声称容器镜像已构建运行。Compose 结构、Unix Socket 协议和 SDK 的实际依赖导入分别检查；镜像构建与真实频道连接留给全新服务器的仅采集验证阶段。
- 本次没有连接生产交易所下单、修改服务器配置或自动开启实盘。

待核对通知保存为 `execution_wait`，复用已有本地重试与动作恢复。再次检查使用已保存的解释，不重新请求模型；动作结果不明时只核对，不盲目再次提交。未提交任务继续受原消息 TTL 约束，已提交动作的恢复由原订单账本负责。

已确认事件和投递按信号保留期清理；未确认投递、仍在等待的信号和活跃交易原卡保留证据。不要直接删除采集缓冲或数据库来处理积压。

订单恢复只在提交尚未发送的入场腿之前再次检查来源准入；断线/缺口暂缓提交，观察模式、配置撤销或已收到的结束通知取消未提交部分。已发送但结果不明的订单仍先查询，减仓和平仓保护不受该入场检查阻止。正常进程重启保留激活边界；操作员停止再启用交易员会建立新边界，停用期间消息不补开仓。

重新启用后，旧卡片发生的最新管理编辑仍可进入解析与目标核验，但该卡片不能绕过新启用边界再次开仓。
