# 采集恢复与日志中心

## 本次更新

Gateway 原始接收回调先按操作码、事件名称分流，控制帧的数组、布尔值、数字不再进入消息字段读取。目标消息的格式或持久化错误会停止新增风险并记录错误类别；不静默丢弃。SDK 继续管理网络重连。

接收任务退出会清理恢复任务、关闭旧客户端、失效旧代次回调。重新应用相同凭证时，已结束且非认证失败的任务可以受控重建；健康任务不重连，认证失败不反复登录，缓冲故障不通过重连绕过。重新连接后的缺口核验、执行启用边界保持原规则。

本次没有调整作者预设、信号解释、仓位计算、交易所下单、止盈止损或订单恢复算法。不使用真实下单验收。

## 更新已有服务器

建议先在 Discord 设置中手动选择“仅采集验证”，再执行：

```bash
cd /opt/nofx && ./start.sh update
```

更新保持 `.env`、数据库、密钥、邮件配置、采集缓冲、交易配置和已保存运行模式。增加 `system_events`、`log_cleanup_tickets` 及交易事件关联字段；不重置数据、不导入旧文本日志、不补执行历史信号。

采集器镜像增加 `diagnostics.py`。诊断缓冲是共享持久目录内的独立 `diagnostics.db`，不复用交易事件 outbox。只有后端在配置 RPC 中声明 `diagnostics_v1` 后才发送诊断帧。后端入库后确认，重传按事件 ID 去重。

## 验收顺序

1. 设置 → Discord 中分别检查本地通信、Gateway、配置应用版本和频道状态。本地通信健康不等于 Gateway 正常。
2. 等待持续心跳、版本一致、频道核验完成。存在 `gap`、`forbidden`、`buffer_failed` 等状态时先处理原因，不启用新增风险。
3. 从导航进入“日志中心”，筛选 `collector` 或 `discord`，检查连接、恢复、配置事件。
4. 等待至少一条启用后的真实新消息，在“交易日志”中验证 `source.received`、`source.delivery.started`、解释与判断结果。点击“查看完整链路”查看不可变消息、投递快照、AI、动作与订单证据。
5. 没有新消息时结论为“等待实时链路验收”，不能以初始化历史基线代替。观察期间积压不会在切换正常执行后补下单。
6. 由用户确认后恢复“正常执行”。已有交易的保护与订单恢复不因采集状态改变而停止。

本地环境如无 Docker，Go/Python/前端测试及部署脚本模拟不能替代目标 Linux 容器验收。

## 页面与筛选

`/logs` 需要登录，含系统和交易两类视图。默认近 24 小时、每页 100 条；按时间、级别、模块、交易员 ID、实际频道、事件名称、关联 ID 和摘要过滤。自动刷新间隔 5 秒，历史页暂停刷新，页面刷新只查询应用数据库。

原交易员日志弹窗保留，并提供已带入交易员 ID 的日志中心入口。

系统日志只接收白名单诊断字段，不发布原始 stdout、请求头、凭证或完整 Gateway 报文。涉及交易员的查询、导出和链路均按用户归属限制。全局运行诊断与现有全局 Discord 设置使用相同登录权限。

完整链路只展示已保存证据。缺失集合可能表示尚未产生、无可靠关联或已过保留期；不会用当前配置填充历史快照。大型链路有显式截断提示，应缩小到单个信号查询。原始事件的会话标识和原始载荷不直接开放。

## 事件与诊断字段

- `gateway.state` / `collector.state`：连接状态变化。
- `gateway.error`：`code`、`stage`、`exception_type`、`close_code`、`file`、`function`、`line`；不记录异常文本或变量。
- `channel.state`：频道恢复、ready、gap、forbidden 等状态变化。
- `config.applied` / `config.apply.failed`：采集路由配置应用结果。
- `source.received` / `source.delivery.started`：持久接收与投递；通过 `source_event_id`、`delivery_id`、消息与信号 ID 关联。
- 既有 `copytrade.*`：解释、风险、执行与恢复事件，继续使用原事件表。
- `email.alert.accepted` / `email.alert.failed`：SMTP 接受或发送失败；接受不代表到达收件箱。
- `logs.settings.saved` / `logs.cleanup` / `logs.retention`：保留设置与清理审计。

同一故障 60 秒内记录首次发生，窗口结束追加重复计数。正常心跳、健康探测和每次轮询检查不会逐条写入日志。系统事件单条不超过 16 KiB；截断可见。诊断写入失败计数与 stderr 后备信息明确表示追踪可能不完整，不改变已成功的订单结果。

## 导出与清理

导出 CSV 或 JSONL，遵循筛选与用户权限。固定 ID 上界、每批 500 条、最多 100,000 条；超过上限要求缩小时间范围。CSV 转义换行、引号和公式起始字符。页面校验导出记录数，不将并发清理造成的短文件当成完整导出。

默认保留：

| 数据 | 保留 |
| --- | --- |
| 系统日志 | 30 天，可选 7 / 30 / 90 天 |
| 交易事件、终态信号 | 90 天，保留现有环境变量覆盖 |
| AI 原文、原始消息、媒体 | 30 天，保留现有环境变量覆盖 |
| 接收、投递审计 | 至少 30 天，默认沿用信号 90 天 |
| 活跃、待处理或待确认的关联证据 | 生命周期保护，不能仅按年龄删除 |
| 交易上下文、动作、订单、去重记录 | 不由日志中心删除 |

媒体文件按内容哈希共享；存在需保护证据的交易或信号时，媒体清理保守暂停，防止删除仍用于恢复的图片。

系统日志每小时批量清理，有 512 MiB 逻辑内容软上限；容量清理可能缩短日期保留范围。显示最早可用记录及逻辑用量。清理系统日志需要先预览再确认：预览凭据绑定用户、截止时间、记录上界，10 分钟过期且只用一次。并发新日志不被删除；清理后记录新的操作审计。清理不改变采集进度、交易账本或执行模式。

文本日志使用 `data/nofx.log`，达到 50 MiB、跨 UTC 日期或达到年龄上限轮转，活动文件与备份总共最多 5 份，最长 30 天。Compose 每服务 stdout 为 20 MiB × 5。大小与份数可能缩短实际保留时间。旧日期文本日志只按年龄清理，不导入网页。

删除数据库行不代表立即缩小 SQLite 文件；不在运行中执行阻塞式 VACUUM。

## 常见故障

- `GATEWAY_TASK_FAILED`：查看异常类型和代码位置；已结束的任务可通过重新保存采集配置重建。新版本已修复非消息载荷导致的异常。
- `GATEWAY_AUTH_INVALID`：由用户核验或更新凭证；系统不循环登录。
- `MESSAGE_PAYLOAD_INVALID`：订阅消息结构损坏，停止采集并保留诊断，需确认载荷处理兼容性。
- `EVENT_BUFFER_FAILED`：检查磁盘和缓冲容量，先解决持久化问题；不要删除 outbox 强行继续。
- `diagnostic_failures > 0`：诊断记录或传输曾失败；消息 outbox 独立保存，不能据此推断订单失败。检查恢复后的链路证据。
- 本地通信正常、Gateway 不正常：容器能响应不代表有实时消息，需同时核对心跳与频道。
